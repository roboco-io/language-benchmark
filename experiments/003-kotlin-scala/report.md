## 사전 기준 대조

사전 등록 판정 규칙(README "주 지표와 사전 판정 기준")은 두 언어(Kotlin, Scala)만 비교 대상으로 둔 대시보드 종합 점수의 언어별 순위를 주 지표로 둔다. 종합 점수는 24개 지표를 같은 무게로 더하고, 두 언어 사이에서 값이 같은 지표(상수 지표)는 뺀다. Sonnet에서는 `pass_rate`·`iterations`·`error_rate`·`soak_error_rate`·`followup_pass`가, Opus에서는 `pass_rate`·`iterations`·`followup_pass`가 상수였다. `interventions`는 기록하지 않은 빈 칸이라 점수에 들어가지 않는다. run 간 범위는 반복 번호(1·2·3)별로 그 반복의 run만으로 종합 점수를 다시 계산한 세 값의 최솟값-최댓값이다(EXP-001·EXP-002와 같은 방법).

두 언어만 정규화하면 각 지표에서 더 나은 언어가 1, 나쁜 언어가 0을 받는다. 그래서 종합 점수는 "상수가 아닌 지표 중 그 언어가 앞선 지표의 비율"에 가깝다. 점수 차이의 크기가 지표값 차이의 크기를 반영하지 않으므로, 아래 지표별 비교와 10개 언어 순위를 함께 읽어야 한다.

| 모델 | 1위 (점수, 반복별 범위) | 2위 |
|------|------------------------|-----|
| Sonnet 5.5 | Scala 0.556 (0.556-0.722) | Kotlin 0.444 (0.278-0.444) |
| Opus 5.5 | Scala 0.550 (0.450-0.600) | Kotlin 0.450 (0.400-0.550) |

| 사전 기준 | 관측 | 충족 여부 |
|----------|------|----------|
| (1) 같은 언어가 두 모델 모두 1위, 2위와 범위 비중첩 | Scala가 두 모델 모두 1위. Sonnet은 Scala 최솟값(0.556)이 Kotlin 최댓값(0.444)보다 높다. Opus는 Scala 최솟값(0.450)이 Kotlin 최댓값(0.550)보다 낮아 범위가 겹친다 | 미충족(Opus에서 겹침) |
| (2) 1위가 다르거나 범위가 겹침 → 부분 지지/보류 | 1위는 같고 Opus에서 범위가 겹친다 | 충족 → 부분 지지 |
| (3) 합격률 0인 언어 별도 표기 | 해당 없음. 본 과제 12/12, 후속 과제 12/12 합격 | — |

판정은 "부분 검증(탐색)"이다. 민감도 확인으로 상수 지표를 빼지 않고 다시 계산해도 Scala가 두 모델 모두 1위(Sonnet 0.652, Opus 0.609)이며, Sonnet은 범위가 겹치지 않고(0.609-0.783 대 0.435-0.565) Opus는 겹친다(0.522-0.652 대 0.478-0.609).

- 직접 관측한 사실: 두 언어 모두 두 모델에서 사실상 첫 시도에 완주했다(본 과제 11/12, 후속 12/12). 언어 차이는 완주 여부가 아니라 과정 지표(Kotlin 우세)와 런타임 지표(Scala 우세)가 서로 반대 방향으로 나타난 데서 드러났다.
- 가능한 설명: Kotlin + Spring Boot는 에이전트가 익숙한 Spring 관례(EXP-002 Java와 같은 프레임워크)를 그대로 써서 구현이 빠르고 짧았을 수 있다. 반면 Spring Boot의 자동 구성과 Hibernate가 JVM 위에서 메모리·콜드 스타트 비용을 키웠다. Play + Slick은 구성이 가볍고 의존성이 적어 유휴 메모리와 기동 시간이 작았다. Opus Kotlin 두 run의 높은 메모리·오류율은 앱 설정(커넥션 풀·스레드 설정) 차이에서 왔을 수 있으나, 로그가 없어 확인하지 못했다. 이 설명들은 언어와 지정 스택을 분리하지 못한다.
- 확인에 필요한 비교: 같은 언어 안의 스택 변경(Kotlin + Ktor, Scala + http4s), 부하 오류의 응답 코드를 남기는 측정, 더 어려운 과제(합격률 천장 해소).

## 한계와 교란 변수

- 표본·과제 범위: 과제 하나, 언어×모델 셀마다 3회다. 12/12 합격은 이 과제에서의 관측이며 일반적인 높은 성공률을 뜻하지 않는다.
- 두 언어 비교의 정규화: 두 언어만 정규화하면 지표마다 0 또는 1이 되어, 작은 차이와 큰 차이가 같은 무게를 받는다. 판정이 이 방식에 민감하다는 점을 감안해 지표별 값과 10개 언어 순위를 함께 보고했다.
- 오염 검사 1건: `opus55-scala-3`의 세션이 하네스 디렉터리 이름 목록을 한 번 조회했다(`ls`). 다른 앱의 파일이나 채점 정본을 연 호출은 없으므로 결과에 포함했다(`runs/deviations.md`).
- Fargate 인프라 실패: Graviton4 Spot 용량 부족(`cpu-unavailable`)과 Spot 회수로 5 run이 첫 측정에서 측정값 없이 끝났다. 측정값이 하나도 없는 실패만 같은 사양으로 다시 측정했고(최대 4라운드), 12/12 Graviton4에서 측정했다. 시도 기록은 `runs/fargate/fargate-attempts.csv`에 있다.
- 빌드 도구 다운로드: sbt는 프로젝트가 지정한 sbt·Scala 컴파일러를, Gradle Kotlin 플러그인은 Kotlin 컴파일러를 의존성처럼 내려받는다. 이것은 Maven 플러그인 다운로드와 같은 범주라 막지 않았다. Gradle wrapper가 Gradle 배포판을 받는 것은 STACK 문구("설치된 `gradle` 명령")로 막았다. Coursier·Gradle 캐시는 run 사이에 공유된다(EXP-002의 Maven `~/.m2`와 같은 조건).
- 노출: `claude-native`는 비격리이며 실험자 글로벌 지침(`~/.claude/CLAUDE.md`), 사용자 스킬, MCP가 모든 조건에 같게 노출됐다.
- 계측: `cost_usd`는 청구액이 아닌 대리지표다. 취약점 수는 Trivy 이미지 스캔(OS 패키지와 이미지 안 jar 포함)과 osv-scanner의 합이며, 대부분 베이스 이미지(`eclipse-temurin:25-jre`)와 Spring·Play 의존성 버전에서 나왔다. `opus55-kotlin-3`은 `eclipse-temurin:25-jre-noble`을 써서 32건으로 적었다.

## 결론 및 후속 실험

- 결론: 이 RealWorld 과제에서 Scala(Play)는 두 모델 모두에서 Kotlin(Spring Boot)보다 종합 점수가 높았지만, Opus에서는 반복별 범위가 겹쳐 차이를 확정하지 못했다. Kotlin은 구현이 더 빠르고 쌌고, Scala는 결과물의 메모리·콜드 스타트·메모리 증가가 더 작았다. 합격률은 두 언어 모두 100%로 천장에 닿았다. 10개 언어 탐색적 비교에서 두 언어는 모두 중하위였고, C#·Go·Rust가 상위를 지켰다.
- 후속: 같은 언어 안의 스택 변경 비교(Kotlin + Ktor), 부하 오류 원인을 남기는 런타임 측정, 반복 수 확대, 10개 언어를 같은 시점에 다시 실행하는 확인 실험.
