## 사전 기준 대조

사전 등록 판정 규칙(README "주 지표와 사전 판정 기준")은 대시보드 종합 점수(24개 지표 균등 가중, 언어 간 min-max 정규화)의 언어별 순위를 주 지표로 둔다. 한 언어가 두 모델 모두에서 1위이고 2위와의 차이가 run 간 범위와 겹치지 않으면 "지지", 1위가 다르거나 범위가 겹치면 "부분 지지" 또는 "결론 보류"다. 보고서 형식의 판정어는 "부분 검증"으로 적는다. run 간 범위는 반복 번호(1·2·3)별로 그 반복의 run만으로 종합 점수를 다시 계산한 세 값의 최솟값-최댓값이다.

종합 점수의 반복별 범위는 반복마다 5개 값만으로 정규화하므로 흔들림이 크다. 범위 판단은 3회 반복에서 나온 탐색적 근거이며 통계적 유의성 검정이 아니다.

언어별로 보면 두 모델에 공통인 경향이 있다. C++은 구현 시간(중앙값 Sonnet 13.9분, Opus 13.6분)과 토큰이 가장 많았지만 유휴·피크 메모리가 가장 작았고(피크 약 13 MiB) 처리량도 상위였다. Python은 처리량이 가장 낮고(511·697 rps) 콜드 스타트가 가장 길었다(1.3·1.8초). ## 관측과 설명

- 직접 관측한 사실: 이 과제는 다섯 언어 모두 두 모델에서 첫 시도에 거의 항상 완주됐다. 언어 차이는 완주 여부가 아니라 구현 시간·비용과 결과물의 런타임 특성에서 나타났다.
- 가능한 설명: 종합 점수는 24개 지표를 같은 무게로 더하므로, 결과물 지표(처리량·메모리·이미지 크기 등)가 많은 언어(Go·Rust·C++)에 유리하다. Python·TypeScript는 과정 지표(구현 시간·비용)에서 앞서도 결과물 지표 다수에서 뒤져 하위가 됐다. 모델 간 1위가 갈린 것은 언어 자체보다 run별 구현 선택(예: Opus Rust의 메모리 사용, Go soak 메모리 증가 134-373 MiB인 run)의 분산일 수 있으며 n=3으로는 분리하지 못한다.
- 확인에 필요한 비교: 가중치를 바꾼 민감도 분석(대시보드에서 가능), 더 어려운 과제(합격률 천장 해소), 반복 수 확대.

## 한계와 교란 변수

- 표본·과제 범위: 과제 하나, 언어×모델 셀마다 3회다. 30/30 합격은 이 과제에서의 관측이며 일반적인 높은 성공률을 뜻하지 않는다.
- 런타임 측정 환경 변경(사전 등록 이탈): 설계는 로컬 Docker 순차 측정이었으나 실험자 결정으로 Fargate Spot ARM64에서 전면 재측정했다. 앱 태스크 2 vCPU(하드 제한)·앱 메모리 1 GiB, 부하 태스크 4 vCPU, 같은 서브넷이다. 측정 전에 앱·부하 태스크가 모두 Graviton4(CPU part 0xd4f)인지 확인하고 아니면 태스크를 교체했다(30/30 Graviton4). 콜드 스타트 시작점(로컬 `docker run` 직전, Fargate 앱 컨테이너 StartedAt)과 컨테이너가 보는 CPU 수(로컬 전체 코어, Fargate 2개)가 달라 로컬 값과 직접 비교할 수 없다. 로컬로 끝낸 2건(`opus55-python-1`, `sonnet55-go-1`)은 `runs/runtime-local-*`에 비교용으로만 남겼다. 예: `opus55-python-1` 유휴 메모리 로컬 369 MiB, Fargate 144 MiB, rps 로컬 600, Fargate 740.
- 후속 과제 하네스 결함: 후속 과제가 앱을 `cp -R`로 복사해 원 run의 `build/CMakeCache.txt`가 따라왔고 C++ `start.sh`의 cmake가 경로 불일치로 실패했다. C++ 6건 중 3건은 에이전트가 직접 해결, 2건은 문제를 만나지 않았고, `sonnet55-cpp-3-fu`만 실패했다. 조건이 모든 run에 같았으므로 실패로 유지했다. `build/`만 지운 사본은 14/167로 통과했다.
- 툴체인: govulncheck v1.9.0이 go1.26.9로 빌드돼 Go 1.27.2 앱에서 실패해 같은 버전을 go1.27.2로 재빌드했다(Fargate 측정의 정적 분석은 모두 재빌드 후). 실험 머신 DNS가 간헐적으로 실패해 Fargate 측정 6 run을 다시 실행했다(앱 문제 아님, `runs/fargate/fargate-attempts.csv`).
- 노출: `claude-native`는 비격리이며 실험자 글로벌 지침(`~/.claude/CLAUDE.md`), 사용자 스킬, MCP(browsermcp, context7, exa)가 모든 조건에 같게 노출됐다.
- 계측: `cost_usd`는 청구액이 아닌 대리지표다. 취약점 수는 trivy 이미지 스캔(OS 패키지 포함)과 언어 스캐너 합이므로 베이스 이미지 선택의 영향이 크다.

## 결론 및 후속 실험

- 결론: 이 RealWorld 과제에서 언어 간 종합 점수 차이는 있었다. Go는 두 모델 모두 상위 2위 안에 들었고 Python은 두 모델 모두 최하위였다. 그러나 1위는 모델마다 달랐고(Sonnet Rust, Opus Go) 순위도 모델 간에 일치하지 않아 가설의 "순위가 같다" 부분은 지지되지 않았다. 합격률은 모든 언어에서 100%로 천장에 닿아, 바이브 코딩 적합성의 차이는 완주 가능성보다 구현 비용과 결과물 품질에서 나타났다. Opus 5.5는 Sonnet 5.5보다 비용이 약 2배, 시간이 약 1.8배였지만 본 과제 합격률 이득은 없었다.
- 후속: 합격률 천장을 없앨 더 어려운 과제, 반복 수 확대, 가중치 민감도 분석, 후속 과제 복사에서 빌드 산출물 제외(하네스 수정).
- 동기화: catalog·ROADMAP·4개 README·번역·대시보드는 이 보고와 같은 커밋 묶음에서 반영한다.
