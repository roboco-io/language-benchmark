## 사전 기준 대조

사전 등록 판정 규칙(README "주 지표와 사전 판정 기준")은 세 언어(Java, PHP, C#)만 비교 대상으로 둔 대시보드 종합 점수의 언어별 순위를 주 지표로 둔다. 종합 점수는 24개 지표를 같은 무게로 더하고, 세 언어 사이에서 값이 모두 같은 지표(상수 지표)는 뺀다. Sonnet에서는 `pass_rate`·`iterations`·`followup_pass`가, Opus에서는 여기에 `error_rate`·`soak_error_rate`가 상수였다. `interventions`는 기록하지 않은 빈 칸이라 점수에 들어가지 않는다. run 간 범위는 반복 번호(1·2·3)별로 그 반복의 run만으로 종합 점수를 다시 계산한 세 값의 최솟값-최댓값이다(EXP-001과 같은 방법). 반복별로 다시 정규화하므로 전체 점수가 반복별 범위 밖에 놓일 수 있다.

## 관측과 설명

- 직접 관측한 사실: 세 언어 모두 두 모델에서 첫 시도에 완주했다. 언어 차이는 완주 여부가 아니라 구현 시간·비용과 결과물의 런타임 특성(메모리, 콜드 스타트, 처리량, 이미지)에서 나타났고, C#은 과정 지표와 결과물 지표 대부분에서 동시에 앞섰다.
- 가능한 설명: C#이 과정과 결과물 양쪽에서 앞선 것은 ASP.NET Core 최소 API·EF Core 조합의 보일러플레이트가 작고(코드량·의존성 최소), .NET 런타임이 JVM보다 유휴 메모리·콜드 스타트가 작기 때문일 수 있다. Java의 낮은 점수는 JVM 특성(메모리, 콜드 스타트, 빌드 시간)이 결과물 지표 여러 개에 함께 반영된 결과다. PHP는 요청 처리 모델(Octane 워커 + FrankenPHP)에서 처리량이 낮고, 지정 스택의 공식 이미지가 큰 Debian 기반이라 취약점·이미지 지표가 나빴다. 이 설명들은 언어와 지정 스택·에이전트가 고른 베이스 이미지를 분리하지 못한다.
- 확인에 필요한 비교: 같은 언어 안에서 스택·베이스 이미지를 바꾼 비교, 가중치 민감도 분석(대시보드에서 가능), 더 어려운 과제(합격률 천장 해소).

## 한계와 교란 변수

- 표본·과제 범위: 과제 하나, 언어×모델 셀마다 3회다. 18/18 합격은 이 과제에서의 관측이며 일반적인 높은 성공률을 뜻하지 않는다.
- PHP 채점 포트 결함(재실행): FrankenPHP(Laravel Octane)는 앱 포트와 함께 관리 포트를 열고, `measure.sh`가 `lsof`의 첫 포트(관리 포트)로 채점해 모든 요청이 404였다. `sonnet55-php-1`(40분 상한 소진)과 진행 중이던 `opus55-php-1`을 무효로 하고, 채점이 주입한 `PORT`를 우선 쓰도록 고친 뒤 두 run을 iteration 1부터 다시 실행했다. 결함은 PHP 전체에 같게 작용했고 결과를 보고 고른 재실행이 아니므로 선택 편향은 없다고 판단한다. 무효 run의 앱도 고친 채점으로는 `13,154`였다.
- C# 스캐너 결함(측정 전 수정): C# 앱 6개가 모두 `.csproj`를 하위 디렉터리에 두어 `dotnet list package`가 프로젝트를 찾지 못했다. 스캐너가 하위 프로젝트를 찾고 `restore`하도록 고치고, 알려진 취약 패키지로 탐지를 확인한 뒤 측정했다. 에이전트 run과 채점에는 영향이 없다.
- Fargate 인프라 실패: `opus55-csharp-2`(ECR pull 시간 초과, Graviton4 미확보)와 `opus55-php-3`(Graviton4 미확보)가 측정값 없이 끝나 같은 사양으로 다시 측정했다. 18/18 Graviton4에서 측정했다.
- 노출: `claude-native`는 비격리이며 실험자 글로벌 지침(`~/.claude/CLAUDE.md`), 사용자 스킬, MCP가 모든 조건에 같게 노출됐다.
- 계측: `cost_usd`는 청구액이 아닌 대리지표다. 취약점 수는 Trivy 이미지 스캔(OS 패키지 포함)과 언어 스캐너의 합이고 언어마다 스캐너가 다르므로, 언어 간 차이는 주로 베이스 이미지 선택의 차이다. PHP의 `trivy.json`은 용량 때문에 `trivy.json.gz`로 보관했다.

## 결론 및 후속 실험

- 결론: 이 RealWorld 과제에서 Java·PHP·C# 사이의 종합 점수 차이는 컸고, C#은 두 모델 모두에서 2위와 범위가 겹치지 않는 1위였다. C#은 구현이 가장 빠르고 쌌으며, 결과물도 메모리·이미지·의존성이 가장 작고 처리량은 상위였다. Java와 PHP의 순서는 모델마다 바뀌어 구별되지 않았다. 합격률은 세 언어 모두 100%로 천장에 닿았다. Opus 5.5는 Sonnet 5.5보다 비용이 약 2.3배, 시간이 약 1.5배였지만 합격률 이득은 없었다. EXP-001과 합친 탐색적 8개 언어 비교에서도 C#은 두 모델 모두 1위였으나, Sonnet에서는 Rust·Go와 범위가 겹친다.
- 후속: 합격률 천장을 없앨 더 어려운 과제, 반복 수 확대, 같은 언어 안의 스택·베이스 이미지 변경 비교, 8개 언어를 같은 시점에 다시 실행하는 확인 실험.
- 동기화: catalog·ROADMAP·4개 README·번역·대시보드는 이 보고와 같은 커밋 묶음에서 반영한다.
