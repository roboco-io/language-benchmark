# language-benchmark 설계 문서

- 작성일: 2026-10-17
- 대상 리포: `roboco-io/language-benchmark` (신규, public 예정)
- 자매 리포: `roboco-io/coding-agent-benchmark` (로컬 경로 `roboco-io/research/vibecoding-token-experiments`, 이하 "기존 리포")

## 1. 의도

이 리포가 답하려는 질문은 "바이브 코딩으로 백엔드를 만들 때 어떤 언어가 가장 적합한가"이다. 여기서 바이브 코딩은 사람이 코드를 직접 쓰지 않고 코딩 에이전트(Claude Code)가 빈 저장소에서 완성까지 구현하는 방식을 뜻한다. 기존 리포는 언어를 TypeScript로 고정하고 모델·하네스 조합을 비교했다. 이 리포는 반대로 모델·하네스를 고정하고 구현 언어를 바꿔 비교한다.

성공의 기준은 대시보드 한 화면에서 언어별로 런타임 속도, 메모리 사용량, 구현 속도, 안정성, 그리고 아래 2절의 추가 지표가 한눈에 비교되는 것이다. 사용자는 이 결과로 "바이브 코딩 백엔드에 어떤 언어를 쓸지"를 판단한다.

## 2. 목표, 비목표, 실패 조건

### 목표

같은 과제(RealWorld 백엔드 API)를 Rust, C++, Python, Go, TypeScript 5개 언어로 구현하고, 다음 지표를 모두 같은 기준으로 측정한다. 사용자가 2026-10-17 대화에서 모든 지표를 포함하기로 결정했다.

| 묶음 | 지표 | 측정 방법(요지) |
|---|---|---|
| 만드는 과정 | 구현 속도 | 첫 프롬프트부터 채점 통과까지의 벽시계 시간 |
| 만드는 과정 | 비용 | 토큰 대리지표와 API 단가 환산 비용(실패 run 포함). 구독으로 실행하므로 실제 청구액이 아니다 |
| 만드는 과정 | 반복 횟수 | Ralph loop가 통과까지 돈 iteration 수 |
| 만드는 과정 | 사람 개입 횟수 | 실험자 수동 개입 기록 |
| 만드는 과정 | 구현 안정성(재현성) | 같은 조건 3회 반복의 합격률과 편차 |
| 결과물 | 런타임 속도 | 고정 부하에서 처리량(RPS)과 지연(p50/p95/p99) |
| 결과물 | 메모리 사용량 | 유휴 RSS와 부하 중 최대 RSS |
| 결과물 | 런타임 안정성 | 부하 중 에러율, 장시간 부하에서 메모리 증가량 |
| 결과물 | 코드량·의존성 | 언어별 LOC(테스트 제외), 직접 의존성 개수 |
| 결과물 | 빌드·배포 | Docker 빌드 시간, 이미지 크기, 콜드 스타트(기동부터 첫 정상 응답까지) |
| 결과물 | 보안 | 언어별 의존성 취약점 스캐너 결과 건수 |
| 결과물 | 유지보수성 | 완성된 코드에 기능 하나를 추가하는 후속 과제의 시간·비용·성공 여부 |

"안정성"은 두 의미를 모두 측정한다. 구현 안정성은 에이전트가 매번 완성해 내는가이고, 런타임 안정성은 완성된 서버가 부하에서 버티는가이다.

### 비목표

- 언어 런타임 자체의 순수 성능 비교(Benchmarks Game류)는 목표가 아니다. 측정 대상은 "에이전트가 만든 코드"이므로, 에이전트의 구현 선택이 결과에 섞여 있다는 점을 결과 해석에 명시한다.
- 모델 간 우열 비교는 부차적이다. Sonnet 5.5와 Opus 5.5 두 모델을 쓰는 이유는 언어 순위가 모델에 따라 바뀌는지 보기 위함이다.
- PostgreSQL 등 운영 DB 특성의 비교는 하지 않는다(SQLite 고정).

### 실패 조건

언어 간 측정 조건이 다르면, 기술적으로 표가 채워져도 실패다. 예를 들어 한 언어만 다른 CPU 제한, 다른 부하 시나리오, 다른 채점 정본으로 측정되면 비교가 성립하지 않는다. 또한 한 번의 관측을 "이 언어가 우월하다"는 확정으로 표현하는 것도 실패로 본다(기존 리포의 품질 규칙과 동일).

## 3. 고정 조건 (사용자 결정 사항)

다음은 2026-10-17 대화에서 사용자가 승인한 사항이다.

- **모델과 도구**: Claude Code + Sonnet 5.5(`claude-sonnet-5-5`), Claude Code + Opus 5.5(`claude-opus-5-5`). 둘 다 별도 구독 요금 없이 기존 구독으로 실행한다.
- **언어와 스택**: 아래 표로 고정한다. 선정 기준은 기존 리포의 TS 스택 선정 기준(해당 언어에서 가장 널리 쓰이고 LLM 학습 데이터가 풍부함)을 따랐고, DB는 모든 언어에서 SQLite로 통일한다.

| 언어 | 웹 프레임워크 | DB 접근 | 비고 |
|---|---|---|---|
| TypeScript | Fastify | Prisma | 기존 리포 과제와 동일 |
| Python | FastAPI | SQLAlchemy | uvicorn |
| Go | Gin | GORM | 순수 Go SQLite 드라이버(modernc) |
| Rust | Axum | SQLx | tokio |
| C++ | Drogon | Drogon ORM | CMake, C++20 |

- **TypeScript 처리**: 기존 리포의 EXP-026(Opus 5.5)과 EXP-031(Sonnet 5.5)은 앱 코드가 보존되지 않아(2026-10-17 확인) 결과물 지표를 측정할 수 없다. 그래서 TS도 새 하네스에서 다른 언어와 똑같이 다시 실행한다. 기존 두 실험의 결과(전부 iteration 1 완주, 세션 4-8분대 등)는 "새 하네스가 과거 결과를 재현하는가"를 확인하는 기준선으로만 가져온다. Phase 0에서 새 하네스의 TS run이 완주하지 못하면 실험을 멈추고 원인을 조사한다. 완주했지만 시간·토큰 수치만 다르면 차이를 기록하고 진행한다(설계자 판단).
- **반복 규모**: 언어 5 × 모델 2 × 반복 3회 = 30 run. 프롬프트는 영어 하나로 고정한다(기존 리포의 EN/KO 축은 이번 비교 대상이 아니다).
- **운영 방식**: 기존 리포의 운영 방식을 따른다(아래 6절).
- **배포**: 리포를 roboco-io에 만들고, 대시보드를 GitHub Pages(`roboco.io/language-benchmark/`)로 배포한다.

## 4. 실험 설계

### 4.1 과제와 채점

과제는 기존 리포의 [RealWorld 백엔드 과제](https://github.com/roboco-io/coding-agent-benchmark/tree/main/tasks/realworld-backend)와 같다. 채점 정본도 기존 리포의 Hurl 정본(13파일·154요청)을 그대로 쓴다. 이 정본은 기존 리포의 `.claude/skills/ralph-model-benchmark/assets/harness-hurl/`에 있고 `checksums.md5`로 해시가 고정돼 있다. Hurl 채점은 HTTP 수준에서만 검사하므로 언어와 무관하게 같은 정본을 쓸 수 있다.

프롬프트는 기존 EN 프롬프트를 기반으로 언어별 5개 변형을 만든다. 변형 간 차이는 스택 지정 문단과 기동 명령 규약뿐이어야 하고, 나머지 문장은 바이트 단위로 같아야 한다. 각 변형의 md5를 실험 README에 기록한다.

### 4.2 기동 규약

기존 하네스의 `measure.sh`는 `npm run dev`로 서버를 띄우므로 TS 전용이다. 이번에는 언어와 무관한 규약이 필요하다. 프롬프트는 에이전트에게 다음 두 가지를 요구한다.

1. 저장소 루트의 `start.sh`: 의존성 설치와 빌드를 포함해 서버를 띄우고, 환경변수 `PORT`로 포트를 받는다. Ralph loop 채점에 쓴다.
2. 저장소 루트의 `Dockerfile`: 운영용(release) 빌드 이미지를 만든다. 런타임 측정에 쓴다.

**합격 조건(사용자 결정, 2026-10-17)**: Ralph 게이트는 `start.sh`로 띄운 서버와 `Dockerfile`로 빌드한 컨테이너가 **둘 다** Hurl 154요청을 통과해야 pass로 판정한다. 따라서 합격한 run은 모두 런타임 측정이 가능하다. 이 때문에 구현 속도는 기존 TS 기준선(호스트 채점만)과 정의가 달라지며, TS 기준선과는 "호스트 채점 통과 시점"만 따로 비교한다.

Dockerfile을 에이전트가 쓰게 하는 이유는, 이미지 크기와 빌드 시간도 "바이브 코딩 결과물"의 일부로 측정하기 위해서다. 그 대가로 에이전트가 debug 빌드나 단일 워커 설정을 고르면 런타임 수치가 언어 특성보다 에이전트 선택을 반영하게 된다. 이를 줄이기 위해 하네스는 이미지 안의 빌드 모드와 워커/스레드 설정을 run별로 기록하고, 4.4의 워커 규칙을 프롬프트에 명시한다. (빌더 판단 영역: 이 기록을 자동 추출할지 수동 확인할지)

### 4.3 Ralph loop 실행

기존 리포의 `ralph-model-benchmark` 스킬 하네스(`driver.sh`, `measure.sh`, `run-all.sh`, `smoke.sh`, `bench.env`, cost_guard, watchdog 등)를 복제해 언어 축을 추가한다. 기존 하네스는 `CONDITIONS`(모델)와 `LANGS`(자연어 EN/KO)를 축으로 쓰는데, 이번에는 `LANGS` 자리에 구현 언어 5종을 넣고 프롬프트 변형을 고른다. run 순서는 기존 규칙대로 반복 번호 × 언어 × 모델을 교차한다.

run 상한은 기존 기본값(20분, 진척 없음 300초)을 쓰되, Rust와 C++는 초기 의존성 빌드가 길어 20분이 부족할 수 있다. Phase 0에서 각 언어의 "hello world 수준 빌드 시간"을 측정하고, 상한을 언어 공통으로 다시 정한다(언어별로 다른 상한은 쓰지 않는다).

### 4.4 런타임 측정

채점을 통과한 run의 산출물만 측정한다. 실패 run은 결과물 지표를 "측정 불가"로 둔다.

- **환경**: 모든 서버를 같은 Docker 리소스 제한(예: 2 vCPU, 1 GiB 메모리)으로 띄운다. 측정 머신은 실험자의 macOS Docker Desktop이며, 이는 VM 위의 측정이라 절대값보다 언어 간 상대 비교로 해석해야 한다는 한계를 대시보드에 명시한다. (빌더 판단 영역: 구체 제한값)
- **워커 규칙(설계자 판단)**: "컨테이너에 할당된 CPU 코어 수만큼 워커 또는 스레드"를 모든 언어에 같은 규칙으로 적용한다. Node는 cluster(코어 수만큼 프로세스), Python은 uvicorn workers(코어 수), Go·Rust·C++은 런타임/스레드 풀을 코어 수로 맞춘다. 여러 프로세스가 한 SQLite 파일에 쓰는 충돌은 모든 언어에 WAL 모드와 `busy_timeout` 5초를 똑같이 요구해 다룬다. 이 규칙은 프롬프트 본문에 들어가 md5로 고정된다.
- **데이터 시드**: 측정 전에 고정 시드 스크립트로 같은 데이터(사용자, 아티클, 코멘트, 태그)를 HTTP API로 넣는다. 시드도 API로 넣으므로 언어와 무관하다.
- **부하**: k6로 읽기 위주 혼합 시나리오(아티클 목록, 단건 조회, 태그, 피드)와 쓰기 시나리오(아티클 작성, 코멘트, 즐겨찾기)를 고정 동시성으로 실행한다. 워밍업 후 같은 측정을 3회 반복해 중앙값을 쓴다. 지표는 RPS, p50/p95/p99, 에러율이다.
- **메모리**: 유휴 RSS(기동 후 시드 전), 부하 중 최대 RSS를 `docker stats`로 기록한다.
- **런타임 안정성**: 별도 장시간 부하(예: 10분)를 걸어 에러율과 시작 대비 종료 시점의 메모리 증가량을 기록한다.
- **빌드·배포**: Docker 빌드 시간(캐시 없음), 최종 이미지 크기, 콜드 스타트 시간.
- **코드량·의존성**: `scc` 또는 `tokei`로 테스트를 제외한 LOC, 매니페스트에서 직접 의존성 개수.
- **보안**: `cargo audit`, `npm audit`, `pip-audit`, `govulncheck`. C++는 표준 스캐너가 없으므로 Trivy로 이미지를 스캔하고, 공정성을 위해 다른 언어도 Trivy 이미지 스캔 결과를 함께 기록한다.

### 4.5 유지보수성 후속 과제

채점을 통과한 각 run의 저장소에서, 같은 모델로 새 Claude Code 세션을 열어 기능 하나를 추가하게 한다. 추가 기능은 "코멘트 수정 API(`PUT /api/articles/:slug/comments/:id`, 작성자만 수정 가능)"로 정한다(설계자 판단). 이 기능은 RealWorld 스펙에 없으므로 이 리포에서 Hurl 파일 1개를 새로 작성해 해시를 고정한다. 기존 154요청이 계속 통과하는지(회귀)도 함께 채점한다. 지표는 소요 시간, 토큰 대리지표, 성공 여부다. 실행은 본 실험과 같은 Ralph 하네스를 쓰고 상한은 최대 5 iteration·20분이다. 성공은 새 Hurl과 기존 154요청(start.sh와 Docker 양쪽)이 모두 통과하는 경우이며, 기존 요청이 깨지는 회귀는 실패로 판정한다(설계자 판단).

## 5. 대시보드

대시보드의 첫 화면은 "언어 × 지표" 비교표 하나다. 행은 5개 언어, 열은 2절의 지표이고, 각 칸은 해당 열 안에서의 순위에 따라 색을 칠한다. 색의 판정 기준(열 내 순위, 좋음의 방향)은 범례로 표시한다. 상단 토글로 Sonnet 5.5 / Opus 5.5 / 두 모델 평균을 전환한다.

"어떤 언어가 가장 적합한가"에 답하기 위해 종합 점수를 함께 보여 준다. 종합 점수는 지표별 정규화 값의 가중합이며, 가중치는 화면의 슬라이더로 사용자가 바꿀 수 있게 한다. 기본 가중치는 실험 전에 정해 문서에 고정하고, 가중치가 바뀌면 순위도 바뀐다는 점을 화면에 명시한다. 종합 점수는 해석 보조이며 결론으로 표현하지 않는다(설계자 판단).

그 아래에 지표별 상세 차트(run 단위 분포 포함)와 각 run의 report 링크를 둔다. 실패 run이 있는 언어는 결과물 지표 칸에 "측정 n/3"처럼 표본 수를 표시한다.

기술적으로는 기존 리포 대시보드 방식을 따른다. 정적 `dashboard/index.html`(vanilla JS + SVG, CDN 라이브러리 없음) 하나에 데이터를 싣되, 기존처럼 손으로 고치는 내장 배열 대신 스크립트가 측정 CSV에서 `dashboard/data.js`를 생성하게 한다(설계자 판단: 지표 수가 많아 수작업 갱신은 오류 위험이 크다). 배포는 기존 `pages.yml`과 같은 GitHub Actions 방식이다.

## 6. 운영 방식 (기존 리포에서 가져오는 것)

다음을 기존 리포에서 복제하고, 언어 비교에 맞게 고친다.

- 실험 폴더 규칙 `experiments/NNN-slug/{README.md, report.md, runs/}`, EXP 번호는 001부터 새로 시작한다. 가설 코드는 언어 축 `L-NN`을 주로 쓴다. 기존 리포의 L 축(자연어 EN/KO)과 이름이 겹치므로, 이 리포의 README에 "L은 구현 언어"라고 정의한다.
- `report.md` 헤더 3줄 형식과 판정 어휘(검증, 기각, 보류, 부분 검증, 기준 미달)
- `docs/experiment-quality-rules.md`(채점 정본 격리, 비용 상한, Phase 0, 토큰 dedup, "3/3은 관측값" 원칙 등)
- `templates/`, `hypotheses/catalog.md`, `ROADMAP.md`
- `scripts/update_readme_results.py`와 `hooks/pre-commit`(README 결과 블록 자동 생성, 키 유출 검사)
- `.github/workflows/pages.yml`, 이슈 템플릿(결과 이의 제기, 벤치마크 요청)
- 다국어 README: 원문 한국어(`README.ko.md` 정본), 영어 `README.md`, 일본어, 중국어 간체
- **앱 코드 보관(사용자 결정, 2026-10-17)**: 각 run의 앱 소스를 `experiments/NNN-slug/runs/apps/<run>/`에 커밋한다. 빌드 산출물, 의존성 디렉토리(`node_modules`, `target`, `.venv`, `build` 등), SQLite DB 파일은 제외한다. report는 이 코드에 직접 링크하며, pre-commit 키 검사가 이 코드에도 적용된다.
- CLAUDE.md / AGENTS.md: 기존 내용 중 TS 전용 규칙(`npm run dev` 등)을 언어 공통 규칙으로 바꾼다.

## 7. 제약과 선행 조건

- **툴체인 설치**: 2026-10-17 확인 기준으로 Docker, k6, Hurl, Go, Cargo, Python3는 설치돼 있고 CMake와 Drogon은 없다. C++ run 전에 설치가 필요하다. 에이전트가 run 안에서 툴체인을 설치하지 않도록, 필요한 툴체인은 실험 전에 실험자가 준비하고 버전을 기록한다.
- **Hurl 경로**: 기존 규칙은 `/opt/homebrew/bin/hurl` 절대 경로를 요구하지만, 현재 PATH의 hurl은 `~/.local/bin/hurl`이다. Phase 0에서 어느 바이너리를 정본으로 쓸지 확정하고 버전을 기록한다.
- **구독 레이트 리밋**: 30 run과 후속 과제를 구독으로 돌리므로 사용량 한도에 걸릴 수 있다. 한도 때문에 중단된 run은 기존 규칙대로 "서비스 장애로 인한 보류"로 처리하고 재실행한다.
- **실행 승인**: 기존 규칙대로 실험 실행 전에 사양과 예상 비용을 사용자에게 보고하고 승인을 받는다.

## 8. 완료 기준

1. `roboco-io/language-benchmark` 리포가 생성되고, 6절의 운영 골격이 커밋돼 있다.
2. `roboco.io/language-benchmark/`에서 대시보드가 열리고, 데이터가 없는 상태에서도 5개 언어 × 지표 표의 빈 골격이 보인다.
3. (실험 단계) 30 run과 후속 과제가 끝나고, 결과가 report와 대시보드에 반영된다.

1-2는 이번 요청의 직접 범위이고, 3은 실행 승인 후 별도로 진행한다.

## 9. 빌더에게 맡기는 것

부하 시나리오의 구체 요청 비율과 동시성, Docker 리소스 제한값, 종합 점수 기본 가중치의 구체 값, 빌드 모드 기록의 자동화 여부, 대시보드 시각 디자인 세부는 빌더가 정한다. 단, 정한 값은 실험 실행 전에 문서에 고정하고 실행 후 바꾸지 않는다.
